## User-visible behavior and ownership

Both the normal FilePreviewPane choice flow and the BuiltInFilePreviewPane fallback export now show the same Atomic indeterminate preparation bar, actual copied-byte label and explicit Cancel. Unknown, zero or stale metadata sizes never become percentages. The label uses the existing FileUtils byte formatter; no total/ETA is invented.

A small per-source ExternalPreparationRequest owns synchronous admission, a job ticket and thread-safe StateFlow state. A second click cannot enqueue a competing export before the first coroutine starts. Cancel requests job cancellation and marks Canceling, but keeps choices busy until the helper body and its cleanup finish. The UI does not promise immediate interruption of an arbitrary blocked InputStream read. Close/source changes dispose the specific owner; old callbacks are ticket-checked. Keyed state collection starts fresh for a new request owner rather than retaining the previous source's byte state for a frame. Gallery/editor source changes cancel immediately before replacing the displayed source. Successful once/always rule persistence still follows an actual successful launch; cancellation is not displayed as an opening failure.

ExternalPreviewHelper preserves its old open(node, launch) overload and constructor call forms. The progress overload reports on the IO dispatcher: zero before remote acquisition, the first actual write, throttled updates at100ms, and forced EOF. Bytes advance only after successful writes. Cancellation is checked again after a potentially blocked read before writing/publishing. The monotonic clock defaults to SystemClock.elapsedRealtime; internal clock injection permits deterministic throttle contracts without a UI injection seam.

The existing64MiB actual-copy cap, typed backend failures, direct FILE/SAF/MediaStore URI paths, MIME normalization and temporary read-only launch construction remain unchanged. Direct URI paths add no backend reads or copy-progress events. Unpublished staged copies are removed in the existing NonCancellable IO cleanup. A copy whose launch callback returned successfully stays available for asynchronous readers, including later owner cancellation. It remains eligible for existing bounded pruning after24hours on a later export, at most128 entries per pass; no timer/service or universal cleanup deadline is introduced. Original files, preferences, grants, root policy, dependencies, global queue and operation journal are unchanged.
