## Smallest proposed detector

First slice recognizes **only the exact eight-byte PNG signature**, with a maximum of **eight bytes returned to the detector**. This is the smallest useful prefix for the frozen PNG case. Recognition means a plausible media type, not successful decoding, image safety or structural validity. Unsupported/truncated/nonmatching content remains generic. Do not infer DOCX from ZIP, add engine support, or attempt broad text/encoding heuristics. Before implementation, verify the PNG signature using its primary specification and record that source; this design is not dependency/competitor research.

Skip probing directories, valid normalized MIME, and an extension already recognized by the existing externalMimeType lookup. Preserve accepted #79 authority, including valid MIME conflicting with filename or content. Resolve only the actual user-selected source at opening/explicit Open-with; never invoke the detector from listing, icon colouring, thumbnails, search indexing, Storage or background scans. Keep file identity/name/size/date/access/extras unchanged; use a temporary effective node with only the recognized MIME for this opening session. Do not persist inferred MIME or change user rules automatically.

**Initial backend restriction:** permit only actual backend types FILE, SAF and MEDIASTORE. An existing USB identity can participate only if its actual bound backend is that supported SAF implementation; do not infer support from a path or identity prefix. Keep real FTP/FTPS/SFTP/SMB/WebDAV and Shizuku metadata-only pending explicit prefix-read/close contracts. This is a deliberate incremental capability restriction, not complete U06 or universal remote detection. The existing controlled FTP-ID consumer delegates InMemoryBackend.type=FILE; it exercises the owned stream contract and cannot establish a real network transport result. Add direct supported/unsupported backend tests before source acceptance so this distinction is visible.

Eight bytes is a **caller payload budget**, not a disk/network byte or duration promise. FileSystemBackend returns BufferedInputStream (100–104); SftpBackend180–182 uses sixteen-request read-ahead; provider/OS buffering is independent. Do not advertise an eight-byte network request, timing improvement or no read-ahead. The helper allocates one eight-byte buffer, creates no export/cache file and never uses readBytes/readText/available/mark/reset/seek. A later real export reopens its own stream from the start through the existing capped helper.

## Read and resource ownership

Run selector/openInput/provider.stream/read/close on IO. Capture the caller Job/context explicitly before any NonCancellable ownership region. Check that captured owner before starting acquisition and before/after each read; checking currentCoroutineContext inside NonCancellable would incorrectly ignore Cancel.

A successful InputStreamProvider must be converted to exactly one owned stream and entered into use before a post-acquisition cancellation check can throw. Cancellation must not strand an eager provider between openInput returning and stream(). Some current backends create resources eagerly: FtpBackend105–145 opens the control/data transfer before returning its provider. Its stream close closes the data socket and calls completeTransfer, which requires226/250 (FtpProtocolClient84–85). Prefix-only reads can therefore fail or block transfer finalization. Do not swallow that close failure and claim FTP support or weaken its verified completion checks.

For the initial supported backend set, keep acquisition/use/close in one IO ownership block that cannot discard an acquired provider on a dispatcher-return cancellation boundary. One viable implementation is withContext(NonCancellable + io), with the captured caller-context checks controlling admission and every read. If a provider succeeded while Cancel arrived, still acquire and close its stream before propagating cancellation. Preserve exceptions from acquisition/read/close as unresolved/failure, and rethrow CancellationException. This is a narrow resource-ownership measure, not permission to continue reading after Cancel. Do not pass an acquired provider/stream as a return value across withContext into UI code.

Read at most remaining(8) per bulk call. Short positive reads accumulate; EOF before8 is unresolved. On a zero bulk read, check the captured owner and perform one single-byte read: EOF ends; any returned byte, including zero, advances the prefix. This avoids a busy loop without interpreting NUL as no progress. Check the owner immediately after a blocked read returns and before accepting bytes or publishing a match. Stop at8 without an extra EOF/lookahead read. Always close the owned stream in the IO region, including recognized prefix, EOF, failure and cancellation.

Cancellation does not guarantee that an arbitrary blocking provider read/close immediately returns. Keep UI Close responsive and reject late results; let the IO owner finish cleanup once that call returns or its existing timeout occurs. Do not claim a wall-clock bound, interrupt a provider from Main, change permission/root settings or create a universal stream-abort abstraction in this slice. A failed/denied probe produces visible recovery using the raw generic type, suppresses automatic launch for that attempt, and never saves a preference. Unknown-but-readable content is an ordinary generic result, not an access failure.

## UI/session integration without resetting selected content

Keep PreviewSourceSelection as the raw source of truth. Derive rawDisplayed = sourceSelection.forParent(current parent), rawKey = rawDisplayed.previewSourceKey(), and an effective node only when the resolver's completed token exactly matches that rawKey. Never store an inferred-MIME copy as the authoritative parent snapshot. A raw MIME/name/size/date/identity change invalidates only that selected key; lazy extras and an unrelated original-parent change while another source is selected must not restart that selection's export.

Use one small per-call-site resolution coordinator remembered independently of the raw source key. It owns at most one active probe and the latest pending key; cancel an obsolete probe and wait for its actual cleanup before starting the latest pending probe, dropping intermediate requests. This bounds work per live pane during rapid switching. Disposal invalidates its token synchronously, cancels work and never starts pending work. It does not claim a global cross-screen bound or immediate interruption of blocked IO.

Capture the initial FileOpeningPreferences snapshot for the opening session, as current preferred behavior does, but defer targetFor until initial resolution is Ready. Then commit that preferred target exactly once using the effective node: explicit extension override still wins, followed by detected exact MIME, detected family and the original global policy. Known metadata should keep the immediate path and existing visual behavior. A pending first probe shows a real checking state with Close; no app discovery result, engine mount, automatic launch, built-in choice or explicit external handoff is admitted before it finishes. A failed probe enters visible recovery rather than automatically launching/saving a generic target.

Keep the committed route, user mode and automaticAttempted state separate from subsequent type/reader refresh. Once, Always, a return to built-in, same-ID metadata refresh, or a later gallery/editor selection must not re-run the original automatic policy. Preserve saved recreation semantics; do not use a nullable initial remember value that is frozen before resolution, and do not reset automaticAttempted whenever a key changes. Before an automatic attempt, recheck session active, current ready token, original screen identity, one-attempt admission and current compatible handler; capture effective source/rule/target exactly as existing choose does. Always still persists only after actual successful launch, and retains extension-first rule selection.

After the built-in route has mounted, **keep the same BuiltInFilePreviewPane call site mounted**. Do not place it under a new key(effective node) or remove it while refreshing original-parent type metadata. Do not start an original-parent probe merely because that original parent changes while the inner viewer owns another selected image. The existing onOpenExternalForNode(shown) callback already supplies the actual displayed gallery/editor source when the user requests choices: freeze that raw source, switch to manual choices, then resolve only that source if needed. It must not inherit a new automatic launch. Keep the PR85 different-gallery-B and same-ID metadata controls unchanged; broader sibling-list freshness remains outside this slice. A source that changes while the choices panel is active refreshes its effective type/readers but not the committed original preferred target.

Close/disposal must invalidate the coordinator before invoking the parent callback, even if the caller leaves the pane mounted for a frame. Completion, discovery, automatic launch and preference updates all require an active matching token. A stale A completion cannot expose A readers, clear B loading, launch, save a rule, or reopen a dismissed pane. Old cleanup must not clear a newer owner. Do not drive late work merely from a same-ID recomposition.

## Additional evidence before source implementation/acceptance

Retain the parent's four frozen consumers. Add separate helper/request and actual-pane controls before implementing the new paths:

- Exact8-byte PNG recognition on a large non-seekable fixture, with a backend stream that records requested/returned bytes and fails any ninth-byte request. Prove source closure and no temp/export file. Short reads, repeated zero-bulk reads, NUL data, EOF0–7, nonmatching8 bytes and ZIP signatures stay bounded/unresolved.
- Known MIME and known extension perform zero openInput calls. Unsupported real backend types skip probing. Preserve existing MIME normalization/extension mapping and current fake-provider caveats.
- Deferred acquisition cancellation before start creates no resource; cancellation after eager provider creation but before ownership still closes exactly its acquired stream. Acquisition, stream-factory, read and close failures do not launch or save. A controlled blocking read released after Cancel cannot publish a detected MIME; final cleanup is observable before the owner becomes ready again.
- Rapid A→B→C selection admits only the latest pending probe after A drains. B/C loading cannot be cleared by A. Dispose/dismiss before A returns permits no late activity, preference mutation or reopening. Separate actual-pane stale-result control, not only a pure helper ticket test.
- Saved image/png MIME and IMAGE-family targets apply after successful initial detection; explicit extension Ask/Built-in/External rules still win; one automatic launch only. Unknown fallback remains generic. Once/Always retain current rule boundaries and failed launches preserve every preference.
- Existing PR85 six metadata/gallery controls, all PR84 preparation/request consumers, valid-MIME/reader/Settings tests and artifact/static/Lint gates remain required. Verify no full-pane remount/reset or cancellation of a selected B export on original-parent refresh. Physical/provider/real transport and release evidence stay separate.
